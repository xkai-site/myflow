# 休闲关卡游戏离线防作弊架构决策稿

> 本文用于产品、研发、风控和管理层确认架构方向。威胁模型、协议轮廓、容量成本及验证运营细节见同目录附件。

## 1. 结论

推荐采用：

> **服务端权威账本 + 有界离线授权 + 双期限提交 + 声明式原子结算 + 高价值业务分轨。**

客户端、本地时钟、执行过程和通信内容均不可信。客户端上传的是待结算声明，不能直接覆盖服务端状态。方案不追求识别所有作弊，而是保证即使客户端完全失守，付费资产、稀缺奖励和奖励排行榜仍受服务端确定性约束。

### 保护优先级

| 等级 | 对象 | 核心规则 |
|---|---|---|
| P0 | 合法购买、付费货币、付费道具 | 只能来自服务端验证的支付、运营授权或既有账本；合法权益可恢复 |
| P1 | 稀缺活动奖励、奖励排行榜 | 普通离线声明不能直接确权；受资格、库存、统一分配和可验证成绩约束 |
| P2 | 广告奖励、活动进度、可转换资源 | 离线有额度；转为 P0/P1 必须联网 |
| P3 | 普通进度、普通货币、低价值掉落 | 在书面风险预算内宽松结算，优先保障弱网体验 |

可接受少量、孤立且不可规模化的 P3 作弊；不可接受 P0 无来源增加、P1 超发、付费权益永久丢失或客户端自报成绩决定高价值奖励。

## 2. 关键架构决策

### 2.1 24 小时采用双期限，而非相信客户端时间

服务端无法证明操作真实发生在离线后的第 10 小时还是第 30 小时。因此定义：

- `play_expire_at = issued_at + 24h`：产品承诺的候选离线游玩期限；
- `submit_expire_at = play_expire_at + submit_grace`：最终提交期限；
- 首轮建议以 6 小时作为宽限实验起点，并根据弱网分布和风险预算调整，不能视为既定承诺。

处理规则：

1. `received_at ≤ play_expire_at`：正常验证；
2. `play_expire_at < received_at ≤ submit_expire_at`：进入宽限结算，只能使用原授权剩余额度，不能刷新次数或增加随机机会；
3. `received_at > submit_expire_at`：高价值结果不结算，付费预留释放，P3 可按预先公布规则恢复有限的单调进度。

唯一截止证据是服务端持久化接收时间。客户端操作时间不作为证据。宽限期会接受少量可能在第 24 小时后产生的声明，这是以有界风险换取正常玩家体验的显式取舍。

### 2.2 服务端权威经济账本

资产不接受客户端最终余额覆盖。每次同步按业务声明生成追加式账本分录，并维持以下不变量：

- P0 没有合法来源不得增加；
- 同一支付、预留、资格和发奖结果最多兑现一次；
- 一个离线预留只能在一个被接受分支上消费；
- 稀缺奖励不突破库存和活动预算；
- P2/P3 不能绕过联网闸门转换为 P0/P1；
- 运营补发也必须经过可审计账本。

同步接收与结算分离：入口先原子持久化并记录 `received_at`，再由按账号分区的结算服务串行处理。重试返回同一业务结果。

### 2.3 原子业务结算

允许在业务单元之间部分接受，但不得在同一单元内拆分消费与收益：

| 原子单元 | 必须共同结算的内容 |
|---|---|
| 关卡 | 体力/资格、道具消费、通关结果、掉落、活动进度 |
| 广告奖励 | 广告资格、服务端回执、次数和奖励 |
| 商店兑换 | 输入资产、库存/限购、输出资产 |
| 离线付费道具 | 预留、绑定关卡/会话、消费及直接效果 |
| 活动资格 | 候选进度、资格生成和资格池入池 |

每个单元只能产生 `COMMITTED`、`REJECTED` 或 `PENDING`。拒绝关卡结果时不能只扣体力或道具而拒绝相应收益。

### 2.4 分支与离线择优试错

服务端通过账本基线、授权分支和预留绑定，保证只有一个分支能够兑现；但必须承认：攻击者可以本地复制授权、尝试多条路径，只提交收益最好的一条。普通客户端哈希链也不能证明历史未删改或发现未提交分支；它最多检查上传序列连续性、同时提交的冲突链和数据损坏。

离线择优试错在完全离线场景下无法彻底消除，因此：

- 离线结果不得直接取得 P1 或进入奖励排行榜；
- 离线随机收益、尝试额度及其转换价值必须受限；
- 允许离线使用的付费道具不得对应“一次机会决定高价值收益”；
- 真正要求一次机会、隐藏信息、公平竞速或高价值随机掉落的玩法必须短时联网，由服务端锚定尝试或运行/重放状态机。

### 2.5 奖励排行榜必须可验证，而非仅保持联网

推荐由服务端签发竞赛会话、规则版本、初始状态和随机种子，客户端上传带序号的玩家输入，服务端使用确定性状态机重放并生成正式分数。所有可能影响获奖集合的成绩在结榜前必须完成重放。

如果现有玩法无法确定性重放，应设计整数化、状态空间较小的独立竞赛模式，或由服务端运行完整状态机。如果两者均不可行，该玩法不能配置高价值排行榜奖励。

### 2.6 稀缺奖励同时控制经济暴露和公平风险

稀缺奖励默认进入资格池并统一结算，不采用校验通过即全局先到先得。竞技活动按可验证成绩分配；非竞技活动采用预先公示的分层抽签或配额，并保留递补、申诉和异常延迟机制。

必须区分两个结论：

- 库存和预算可以确定性保证“不超发”；
- 正常玩家实际获奖比例取决于资格识别和抗女巫攻击效果，不能被确定性保证。

库存分组比例、污染率阈值、集中度护栏和延迟窗口均应由奖励价值、历史分布、红队实验、抽样误差和审核能力计算后批准。关联信号全部失效时，应退化为统一延迟结算、单账号资格、不可交易或低变现奖励以及抽签/可验证排名，而不是宣称仍能可靠识别“正常池”。

## 3. 系统边界与工程骨架

### 核心对象

- `OfflineGrant`：账本基线、规则版本、双期限、额度和分支；
- `SyncClaim` / `OperationClaim`：幂等同步批次及原子业务声明；
- `Reservation`：付费权益或资格的冻结、消费和释放；
- `LedgerEntry` / `Settlement`：权威账本分录及唯一结算结果；
- `RewardQualification`：活动资格池状态；
- `CompetitionSession`：排行榜输入流和重放结果。

### 授权与协议安全

`OfflineGrant` 采用服务端权威记录加签名/MAC 凭证。高价值结算必须查询服务端授权状态，不能只依赖客户端凭证验签。凭证绑定账号、授权、账本基线、分支、规则版本、双期限和密钥版本。

需支持密钥轮换、按授权/账号/活动/版本/密钥吊销、账号会话绑定、跨账号重放拒绝和旧规则验证器兼容。相同 Claim ID、相同内容返回原结果；相同 ID、不同内容进入幂等冲突处置。

### 工程拓扑

- 多地域就近接入，单账号主地域串行写入；
- 接收日志与结算分离，接收成功即可固定截止资格；
- 账本采用按账号分区的追加式存储，账号内线性一致或可串行化；查询投影最终一致；
- 活动资格先入池，全局预算或强一致库存服务在统一分配时提交配额；
- P0/P1、活动截止和 P3 使用分级队列；积压时优先暂停新高价值资格、合并低价值声明，不丢弃已确认接收的数据；
- 节点或可用区故障可通过地域内同步复制实现已确认 P0/P1 写入 `RPO=0`；若跨地域异步复制，整个地域灾难只能承诺非零 RPO。地域级 `RPO=0` 必须采用跨地域同步确认或全局一致存储，并接受更高延迟和成本。

## 4. 运营处置与验证

### 处置原则

确定性规则负责维持经济不变量；风险模型、设备信号和客户端防护只用于调节额度、延迟发放、确定审核优先级和提高攻击成本。证据不足时采用暂缓、降级和隔离等可逆处置，不直接扣除合法购买权益或永久封禁。

系统必须支持按版本、活动、转换路径和授权密钥暂停签发、暂停兑换、暂停发奖及熔断。申诉成功后能够重放原决策并恢复合法权益。

### 上线前必须验证

1. **账本与状态机**：重复、乱序、分叉、崩溃、部分成功和退款下，不发生 P0 无来源增加、重复兑现或合法购买永久丢失。
2. **双期限**：正常、宽限和最终超期边界结果确定一致；宽限增加的最坏损失不超过书面预算。
3. **离线试错**：在攻击者隐藏失败分支的前提下，P1、排行榜和高价值随机收益仍不被离线路径取得。
4. **排行榜**：所有潜在获奖成绩完成确定性重放；无法重放时禁止配置高价值奖励。
5. **账号农场**：关闭设备关联信号进行压力模拟，总库存不超发；同时测量资格池污染、正常玩家获奖比例和攻击成本，而不是只检查财务损失。
6. **弱网体验**：灰度比较同步失败、暂定结果回退、留存、客服和申诉；阈值在实验前登记。
7. **容量与灾备**：使用实测每日同步次数、批次大小、重试和峰均比校准容量；分别演练节点、可用区及地域灾难，验证各自 RPO/RTO。
8. **隐私和成本**：只保留能改变决策的数据；计算每百万 DAU 的接入、计算、存储、重放和审核成本。

## 5. 进入详细设计的条件

满足以下条件后再进入接口、字段和完整状态机设计：

- 产品确认双期限、宽限风险、最终超期恢复和多设备冲突语义；
- 完成资产来源、消费和转换图，所有通往 P0/P1 的路径均有服务端闸门；
- 奖励排行榜已经选择可重放模式、服务端运行模式或取消高价值奖励；
- 活动负责人批准库存分配方式、公平指标、污染处置和递补规则，并明确不能保证自然人唯一性；
- 授权签名、轮换、吊销、会话绑定、重放防护和旧版本兼容通过安全评审；
- 原子业务边界、预留、分支、补偿和跨服务一致性已经评审；
- 容量、成本、队列背压、结算时延及分级灾备目标已通过压测和演练；
- 申诉、恢复、审计、熔断和隐私责任明确。

####### 2. 主要威胁

1. 伪造通关、分数、奖励、体力消耗或资产变化。
2. 回滚、重放和复制离线状态，重复领取或重复消费。
3. 多设备并行形成状态分叉，并选择性提交有利分支。
4. 修改本地时间，绕过活动、体力和广告限制。
5. 利用弱网重试、服务超时和跨系统部分成功重复发奖。
6. 使用大量账号分别取得合法额度，放大为活动级损失。
7. 通过普通资产转换链路间接取得稀缺奖励。
8. 使用形式合法但实际伪造的成绩进入奖励排行榜。
9. 风控误判正常弱网用户，造成进度、奖励或付费权益争议。
10. 过度采集和长期保存数据，产生隐私及持续成本风险。

风险排序至少考虑：

> 风险 = 单次影响 × 发生可能性 × 可规模化程度 × 不可逆性

####### 3. 目标与非目标

########## 目标

- 保证合法购买可独立确认、补单和恢复。
- 阻止 P0 资产未经授权增加或重复消费。
- 保证 P1 奖励不超库存，且关键资格不由普通离线声明直接决定。
- 保证奖励排行榜不依赖客户端自报最终分数。
- 保持普通关卡在弱网和短期断网下连续可玩。
- 限制单账号、单窗口、转换路径和活动全局的最大损失。
- 建立监测、熔断、申诉、恢复和策略调整闭环。
- 将服务器、存储、客服及人工审核成本控制在批准预算内。

########## 非目标

- 阻止玩家修改其自有设备上的所有本地内容。
- 确定性证明每一局离线游戏真实发生。
- 消灭所有脚本、自动化、账号共享和低价值作弊。
- 对所有玩法强制实时联网。
- 依赖大规模人工审核覆盖全部异常。
- 使用设备指纹证明“一台设备等于一个自然人”。

####### 4. 约束冲突与取舍

| 冲突 | 取舍 |
|---|---|
| 离线体验与服务端权威 | 保留普通闯关连续性，牺牲高价值结果的即时最终确认 |
| 排行榜公平与离线参赛 | 普通离线成绩仅进入个人或非奖励榜，奖励竞争要求服务端权威路径 |
| 稀缺奖励与即时到账 | 离线只积累候选进度，最终发放延迟至联网核验 |
| 严格校验与弱网误伤 | 确定性规则维持不变量，统计模型优先采用可逆处置 |
| 全量检测与成本 | 集中治理可规模化、高影响风险，容忍少量 P3 作弊 |
| 检测覆盖与隐私 | 只收集能够改变决策且具有合法目的的数据 |
| 快速处罚与可恢复性 | 不可逆处罚要求确定性证据或多源高可信证据 |

冲突发生时的优先级为：

1. 隐私及法律义务、合法购买权益；
2. P0 资产和 P1 奖励完整性；
3. 奖励排行榜和竞争公平；
4. 正常玩家核心离线闯关体验；
5. 普通经济与进度的精确性；
6. 处罚每一个作弊者。

####### 5. 成功标准

题面未提供财务损失、误伤、容量和成本基线，因此不承诺未经验证的具体数值。上线阈值必须由责任团队基于实测数据预先登记。

| 维度 | 成功标准 | 主要指标 |
|---|---|---|
| P0 资产 | 不存在无来源增加、重复消费或不可恢复的合法购买损失 | 对账差异、补单、退款、重复消费 |
| P1 奖励 | 不超库存，发放资格和业务结果可审计 | 重复发奖、库存差异、争议率 |
| 排行榜 | 客户端自报成绩不能直接改变获奖集合 | 赛后变更、异常名次、申诉 |
| 弱网体验 | 相对现状不出现超出体验护栏的进度损失或限制 | 同步失败、回退、留存、客服工单 |
| 批量风险 | 即使账号关联信号失效，总损失仍不突破书面预算 | 奖励集中度、转换暴露、活动损失 |
| 成本 | 单位活跃用户和单位同步量成本可持续 | 计算、存储、带宽、审核和客服成本 |
| 隐私 | 数据具有明确目的、最小范围和保留期限 | 权限审计、删除请求、隐私评估 |

## 7. 经济账本与离线同步协议

####### 4. 关键业务流程

########## 4.1 在线确认与离线授权

玩家联网并完成上一轮结算后，服务端签发新的离线授权。授权至少包含：

- `offline_grant_id`：离线授权唯一标识；
- `account_id` 与可选 `device_binding`：所有权及增强约束；
- `base_ledger_version`：本地分支必须基于的权威账本版本；
- `branch_id`：本授权允许提交的唯一经济分支；
- `ruleset_version`：关卡、掉落、活动和转换规则版本；
- `issued_at`、`play_expire_at`、`submit_expire_at`：均为服务端时间，分别表示签发时刻、24 小时候选游玩期限和带宽限的最终接收期限；
- 按资产、玩法和转换路径划分的额度；
- `reservation_id`、资格或随机种子等已预留权利；
- 禁止离线最终完成的高价值操作。

断续联网只有在完成必要结算并取得新授权后才重新计算窗口，普通心跳不能自动延长经济授权。同一账号默认仅允许一个活跃经济分支；新设备申请授权时，应先结算或显式作废旧分支。

########## 4.2 离线运行

- 客户端基于 `base_ledger_version` 形成本地投影。
- 每项声明携带同一授权下单调递增的 `operation_seq`；可选的 `prev_operation_hash` 仅用于检查上传序列连续性、发现同时提交给服务端的冲突链，以及识别传输或本地存储损坏。客户端完全受控时，攻击者可以重建整条哈希链或隐藏未提交分支，因此普通哈希链不能证明历史未被删改，也不能作为恶意防篡改证据。除非未来引入服务端在线锚点或可信硬件签名，否则核心结算不得依赖它。
- 每个 `operation_id` 全局唯一；使用预留权益的操作同时引用 `reservation_id` 和具体关卡/会话。
- 本地时间只用于提示，不决定资格。客户端无法可靠知道服务端是否已经到期，因此 UI 应表述为“预计剩余可结算时间”，并建议在到期前联网。
- 客户端达到确定性额度后必须停止展示新的可结算经济收益；即使被篡改，服务端仍按授权额度截断。
- 客户端保留可恢复的操作声明，不上传最终余额覆盖服务器状态。

########## 4.3 重连与声明式同步

1. 同步批次携带 `claim_id`、`offline_grant_id`、`base_ledger_version`、`branch_id` 和操作范围。
2. 同步入口先验证尺寸、版本和授权归属，再将原始批次及服务端 `received_at` 原子持久化；相同 `claim_id` 重试返回同一接收结果。
3. 若 `received_at ≤ play_expire_at`，批次进入正常验证；若 `play_expire_at < received_at ≤ submit_expire_at`，标为 `GRACE_SUBMITTED`，仍受原额度和原分支约束；若 `received_at > submit_expire_at`，整批标为 `EXPIRED`，不采信客户端操作时间拆分批次，只执行 P3 超期恢复和预留释放。
4. 可结算批次按账号/账本分区串行处理，检查序号连续性、前序哈希、账本基线和兄弟分支。
5. 对账引擎逐项应用操作声明，不接受整体状态覆盖；遇到首个非法或冲突操作时，该操作及其所有后继经济结果拒绝，不能跳过坏操作继续挑选有利后果。
6. 低风险 P3 可快速确认；P0/P1、分叉和异常结果进入延迟处理。
7. 结算生成唯一 `settlement_id` 和新账本版本，客户端以该权威结果重建本地状态，再取得下一授权。

活动和授权是否按时只依据同步入口的**持久化接收时间**，不依据后台处理完成时间、请求发起时间或客户端声称的完成时间。

########## 4.4 结算顺序

结算依次检查：

1. 账本来源、预留、消费和库存不变量；
2. 离线窗口、规则版本、期限和额度；
3. 重放、分叉、多设备并行和过期基准；
4. 活动资格、广告回执及转换路径；
5. 活动全局预算和奖励库存；
6. 风险信号和批量账号聚集情况；
7. 接受、部分接受、暂缓、降级、拒绝或追加联网验证。

确定性规则优先于风险模型。风险模型关闭时，P0/P1 仍必须安全。

####### 5. 时间、活动与广告规则

########## 活动截止

本方案推荐采用公开宽限期：

- 活动结束后停止签发新的活动离线授权。
- 已持有有效授权的候选声明可在公开宽限期内提交。
- 宽限期应覆盖有效活动授权的最大剩余时长，并根据尾部同步流量验证。
- 最终结榜和稀缺发奖在宽限期及积压处理完成后执行。
- 本地声称的完成时间不作为资格依据。
- P1 发放仍需服务端预留资格或可验证路径，宽限期本身不提高声明可信度。

########## 广告奖励

- 优先使用广告供应商服务端回执，并由服务端去重。
- 无回执的离线广告只能产生受限、低价值且不可向 P0/P1 转换的收益。
- 第三方验证故障时标记待确认，不永久损害已获得有效回执的权益。

####### 6. 核心对象、状态机与跨服务一致性

########## 6.1 核心对象轮廓

以下不是完整字段设计，而是保证方案可落地所需的最小对象边界：

| 对象 | 关键标识/属性 | 责任 |
|---|---|---|
| OfflineGrant | `offline_grant_id`、`base_ledger_version`、`branch_id`、`ruleset_version`、`issued_at`、`expires_at`、额度 | 定义一次离线风险窗口 |
| OperationClaim | `operation_id`、`operation_seq`、`prev_operation_hash`、操作类型、关卡/会话引用 | 表达一项待结算操作，而非最终余额 |
| SyncClaim | `claim_id`、授权、操作范围、`received_at` | 作为幂等接收和截止判定单元 |
| Reservation | `reservation_id`、资产、数量、绑定分支/会话、到期时间 | 冻结可离线消费的既有权益 |
| RewardQualification | `reward_qualification_id`、活动、资格池、规则版本、风险状态 | 进入统一分配而非直接占用库存 |
| LedgerEntry | `ledger_entry_id`、来源业务、资产、增减、前后版本 | 构成不可覆盖的权威经济账本 |
| Settlement | `settlement_id`、输入 `claim_id`、结果、原因、输出账本版本 | 记录一次不可重复的结算结果 |
| CompetitionSession | `competition_session_id`、种子、初始状态、输入流、重放结果 | 形成排行榜正式成绩 |

关键唯一约束至少包括：`claim_id`、`operation_id`、`reservation_id`、`reward_qualification_id`、支付凭据和业务发奖结果均只能成功兑现一次。

########## 6.2 主要状态机轮廓

**离线授权：**

`ISSUED → ACTIVE → PLAY_EXPIRED → GRACE_SUBMITTED/SUBMITTED → SETTLING → SETTLED`

异常终态包括：`EXPIRED`、`CONFLICTED`、`REVOKED`。`PLAY_EXPIRED` 表示产品游玩期限结束但仍处于提交宽限；只有超过 `submit_expire_at` 才进入 `EXPIRED`。任何状态都不能由客户端操作时间逆转。

**预留权益：**

`AVAILABLE → RESERVED → CONSUME_PENDING → CONSUMED`

未使用或失败路径：`RESERVED/CONSUME_PENDING → RELEASE_PENDING → RELEASED`。只有获胜分支可以进入 `CONSUMED`；冲突分支不能同时消费，也不能保留其消费后果。

**同步声明：**

`RECEIVED → VALIDATING → ACCEPTED/PARTIALLY_ACCEPTED/REJECTED/EXPIRED/REVIEW_PENDING → APPLIED`

`PARTIALLY_ACCEPTED` 只允许在明确的**原子业务边界**之间截断，不能在同一原子单元内部拆分消费和收益。推荐原子单元如下：

| 原子业务单元 | 必须共同提交和结算的内容 | 失败语义 |
|---|---|---|
| 关卡结算单元 | 入场资格/体力预留、道具消费、随机种子、通关结果、固定与随机掉落、活动进度 | 整体提交或整体拒绝；拒绝时消费不落账、收益不发放 |
| 广告奖励单元 | 广告资格、供应商回执、次数扣减、奖励发放 | 回执无法确认则整体待确认，不先扣次数后拒绝奖励 |
| 商店兑换单元 | 输入资产扣减、库存/限购占用、输出资产增加 | 单一账本事务或 Saga 业务结果，不允许只扣不发 |
| 付费道具离线使用单元 | `reservation_id`、关卡/会话绑定、消费结果及由其直接产生的效果 | 获胜分支整体消费；冲突分支整体释放或拒绝 |
| 活动资格单元 | 候选进度、资格生成、资格池入池 | 入池成功后才消耗对应次数；失败可幂等重试 |

一次同步批次可以包含多个原子单元，因此允许在单元之间部分接受；但一个单元内必须输出唯一 `COMMITTED`、`REJECTED` 或 `PENDING` 结果。对于长关卡，可在开局时仅做预留，最终结算时原子地把预留转换为消费并发放收益；超时或拒绝则释放预留。

**奖励资格：**

`CANDIDATE → ELIGIBLE → ALLOCATING → RESERVED_FOR_WINNER → ISSUED`

风险、撤销和递补路径：`ELIGIBLE/RESERVED_FOR_WINNER → HELD/DISQUALIFIED → REALLOCATED`。库存只有在统一分配阶段才绑定获奖者。

########## 6.3 授权与协议安全

- `OfflineGrant` 采用“服务端存储权威记录 + 客户端携带签名凭证”的混合模式。服务端记录状态、额度、版本和吊销信息；客户端凭证用于接入层快速验签，不能替代权威状态查询。
- 凭证至少覆盖账号、授权 ID、账本基线、分支、规则版本、双期限、额度摘要和 `key_id`，使用服务端 MAC 或数字签名防篡改。任何可导致 P0/P1 变化的结算均须查询服务端授权状态，不能只做离线验签。
- 密钥按 `key_id` 和算法版本轮换；验证端在兼容窗口内同时接受当前和上一把公钥/验证密钥。签发密钥与验证服务隔离，密钥泄露时可按 `key_id` 停止接受并批量吊销相关授权。
- 授权状态支持 `ACTIVE/REVOKED/EXPIRED/SETTLED`。发现漏洞、退款、账号冻结或规则紧急下线时可按授权、账号、版本、活动或密钥批量吊销；已持久化声明按吊销生效时刻和业务不变量处理。
- 同步请求必须使用正常账号会话认证，并将会话账号与授权账号、`claim_id` 命名空间和设备增强绑定交叉校验。跨账号携带授权或声明一律拒绝。
- `claim_id` 在账号范围内永久幂等；推荐由服务端授权前缀加客户端随机数/序号组成，并建立 `(account_id, claim_id)` 唯一约束。相同 ID、相同内容返回原结果；相同 ID、不同内容标记 `IDEMPOTENCY_CONFLICT` 并冻结该授权后续高价值结算。
- `operation_id`、`reservation_id` 和 `reward_qualification_id` 同样包含账号/授权作用域，禁止跨账号或跨授权重放。
- `ruleset_version` 具有明确兼容期限。授权签发时固定版本；在 `submit_expire_at` 前服务端必须保留对应验证器。安全漏洞版本可提前吊销，但需按产品规则释放付费预留并提供非高价值补偿。旧客户端不能获得新授权时应仍可登录、同步既有合法权益并收到升级提示。
- 传输层加密、请求防重放 nonce 和限流用于保护链路，但不改变“客户端内容不可信”的基本假设。

########## 6.4 跨服务一致性

账本接受、库存扣减、发奖和排行榜投影必须对应同一个可审计的唯一业务结果。跨服务发生超时或部分成功时：

- 不通过再次执行完整业务来“尝试修复”；
- 权威服务先记录业务结果和 outbox 事件，下游按业务结果 ID 幂等补齐；
- 投影失败不能反向改变已经确认的资产事实；
- 发奖状态不确定时先暂停，不重复发放；
- 补偿通过反向账本分录完成，不删除或覆盖历史；
- 运营补发也必须经过可审计账本路径，禁止直接修改余额。

## 8. 容量、成本与工程拓扑

####### 8. 初步容量、成本模型与隐私

DAU 约 1,000 万不能直接推出精确峰值，但系统负责人仍应给出可代入实测值的容量模型。以下数字均为**首轮压测假设，不是上线承诺**：

| 参数 | 首轮假设 | 计算/用途 |
|---|---:|---|
| DAU | 10,000,000 | 题目事实 |
| 每 DAU 每日同步批次 `S` | 2～4 | 日批次量 `D × S = 2,000万～4,000万` |
| 每批操作声明 `O` | 20～80 | 日操作量约 `D × S × O`，即 4亿～32亿条；决定是否需聚合低价值操作 |
| 压缩后批次载荷 `B` | 8～32 KB | 日入口原始流量约 160 GB～1.28 TB，不含副本与索引 |
| 峰均放大系数 `K` | 8～15 | 峰值接收 TPS 约 `(D × S / 86400) × K`，约 1,900～6,900 批次/秒 |
| 重试放大 `R` | 1.1～1.5 | 接入和幂等容量乘数 |
| 账本分录/批次 `E` | 3～12 | 日账本分录约 6,000万～4.8亿，必须通过样本验证 |
| 完整人工审核率 | 由 `每日有效审核工时 ÷ 单案平均处理时长 ÷ 日结算批次` 反推 | 必须设置每日硬上限；超过容量即转自动暂缓或分层抽样 |
| 排行榜完整重放 | 100% 覆盖潜在获奖集合，另加分层抽样 | 不要求重放所有普通局 |

容量模型应使用：

- `平均接收 TPS = D × S / 86400`；
- `设计接收 TPS = 平均 TPS × K × R × 安全余量`；
- `日热存储 = 日批次量 × B × 副本/索引系数 + 日账本分录 × 单分录大小`；
- `审核人力 = 每日送审量 × 单案平均处理时长 / 有效工时`；
- `活动最大风险 = 单资格最大价值 × 可进入资格池数量 × 最坏批量放大系数`，并受库存与书面风险预算取小值。

首轮建议保留策略，同样需要法务和成本验证：

- 原始 P3 操作声明热存 7～14 天，随后聚合或删除；
- 高风险原始声明和处置证据热存 30～90 天，再按申诉/合规要求转冷；
- P0/P1 账本、支付、库存和发奖分录按财务与合规期限保存，不沿用 P3 短期策略；
- 排行榜输入流至少保存至赛季结算、申诉窗口结束和审计完成；
- `account_id` 作为主要分区键，并对超级活跃账号设置单账号串行邮箱、限流和独立隔离，避免热点穿透；活动库存按 `activity_id + bucket` 分片，但由统一预算服务维持总上限。

资源成本不应给出脱离云厂商、压缩率和副本策略的金额承诺。应在压测后计算并审批：

> `每百万 DAU 月成本 =（接入 + 队列 + 结算计算 + 热/冷存储 + 重放 + 可观测性 + 审核人力）/ DAU × 1,000,000`

首轮工程目标是：确定性校验占绝大多数请求；昂贵重放和风险模型只覆盖候选获奖集合、异常分层与抽样；人工审核不得成为正常结算链路依赖。

########## 8.1 推荐工程拓扑

- **多地域接入、单账号归属写入。** 客户端接入最近地域；全球目录根据 `account_id` 路由到账号主地域。边缘地域可以验签、限流和持久化接收，但同一账号的账本结算只在一个主地域串行执行。
- **接收与结算分离。** 接入层先把声明写入具备跨可用区副本的接收日志，成功后返回服务端 `received_at`；结算服务消费日志。边缘接收成功但主地域暂不可用时，截止资格不丢失。
- **账本存储模型。** 采用按账号分区的追加式账本和版本化快照；账号分区内要求线性一致/可串行化写入，不使用最终一致覆盖余额。查询投影可以最终一致。
- **账号分区迁移。** 迁移前冻结新离线授权，记录迁移栅栏版本，排空旧分区声明，再把快照和未消费预留转移到新分区；目录切换后旧分区只转发或拒绝写入，防止双主。
- **热点活动库存。** 总库存由单一预算服务或强一致分片计数器维护；资格先进入池，不在请求路径逐个争抢全局库存。统一分配时按 `activity_id + allocation_bucket` 并行计算，再由预算服务原子提交各桶配额。
- **队列与背压。** P0/P1、活动截止和普通 P3 分队列。首轮积压护栏建议：P0/P1 不超过 5 分钟正常流量、P3 不超过 30 分钟正常流量；超过后停止签发新的高价值离线资格、降低 P3 接收频率并合并低价值操作，不能丢弃已确认接收的数据。
- **灾难恢复。** 接收日志和权威账本在地域内跨可用区同步复制，因此节点或单可用区故障可将已确认 P0/P1 写入目标设为 `RPO = 0`。跨地域采用异步复制时，整个主地域不可恢复的灾难只能承诺非零 RPO，实际值由复制延迟分布和演练确定。若业务要求地域级 `RPO = 0`，必须改为跨地域同步确认或全局一致存储，并接受更高写入时延、可用性和成本代价。RTO 同样按可用区故障与地域灾难分别定义。
- **跨地域重复提交。** 所有地域共享或异步汇聚 `(account_id, claim_id)` 幂等索引；在全局索引不可用时，只允许主地域完成高价值结算。两个地域都接收的重复批次最终由账号主地域按唯一约束收敛为一个结果。

########## 8.2 初始结算 SLO

从同步入口完成持久化接收开始计时：

| 类型 | 正常目标 | 峰值/降级目标 | 超时行为 |
|---|---:|---:|---|
| P0 合法购买确认/恢复 | 99% ≤ 1 分钟 | 99% ≤ 10 分钟 | 标记待确认，禁止重复扣款，不丢权益 |
| P0 离线预留消费 | 99% ≤ 5 分钟 | 99% ≤ 30 分钟 | 保持预留，恢复后幂等结算 |
| P1 资格入池 | 99% ≤ 10 分钟 | 99% ≤ 1 小时 | 以 `received_at` 保留资格，不提前发奖 |
| P1 最终发放 | 宽限期结束后 24～72 小时 | 按活动公示上限 | 延迟结榜并通知，不使用未完成结果 |
| P3 普通进度 | 95% ≤ 5 分钟，99% ≤ 30 分钟 | 99% ≤ 2 小时 | 客户端显示待同步，可继续普通玩法 |
| 排行榜候选成绩重放 | 结榜前 100% 完成 | 不满足则延迟结榜 | 未重放成绩不得影响获奖集合 |

SLO 数值为首轮工程目标，必须结合压测、现网基线和成本预算调整；但 P0/P1 安全不变量不能通过放宽 SLO 牺牲。

架构原则：

- 接入层无状态扩展，并通过持久化队列吸收集中重连。
- 按账号或账本分区保持局部顺序。
- 便宜的确定性校验先于昂贵风险分析。
- 普通结果异步处理，支付、稀缺奖励和结榜任务优先。
- 排行榜查询投影与资产账本分离。
- P0/P1 账本及关键决策保留完整审计。
- P3 原始行为采用短期保留、聚合或采样。
- 人工审核仅覆盖关键奖励、重大付费争议、新型攻击和抽样标签。

隐私要求：

- 每类数据必须有明确的防作弊、对账或权益恢复目的。
- 优先使用账号级、假名化和粗粒度数据。
- 不因“未来可能有用”长期保存设备和网络明细。
- 按地区、年龄和平台限制数据使用范围。
- 对数据访问、保留、删除和申诉建立审计流程。
- 删除设备关联数据后，核心经济安全不变量仍须成立。

## 9. 验证、运营与详细设计准入

####### 9. 故障降级与运营闭环

| 场景 | 处理原则 |
|---|---|
| 授权服务不可用 | 已有窗口继续使用；不签发新的高价值权益 |
| 同步入口故障 | 客户端保留声明并安全重试 |
| 结算队列积压 | 先持久化接收，延迟确权；不因处理延迟改变截止资格 |
| 权威账本不可用 | 暂停 P0/P1 最终写入，普通闯关继续 |
| 风险服务不可用 | 保留确定性上限，高风险结果暂缓而非默认放行 |
| 排行榜服务故障 | 延迟结榜和发奖，不使用不完整结果提前确定获奖者 |
| 支付验证故障 | 标记待确认，恢复后从支付平台重新对账 |
| 发现系统性漏洞 | 优先关闭相关兑换、发奖或竞争入口，不关闭普通闯关 |
| 存储压力 | 优先删除低价值遥测和重复原始数据，保留账本、支付及关键审计 |

处置等级从低到高为：

1. 接受但记录风险；
2. 降低后续离线额度；
3. 暂缓高价值兑换或奖励；
4. 要求特定高价值场景联网；
5. 移出当前奖励榜或降级奖励；
6. 限制活动及兑换；
7. 对确定性证据或多源高可信证据支持的持续攻击执行账号处罚。

申诉成功后应能够重放原决策、恢复合法权益并记录策略问题。人工运营重点处理关键名次、稀缺奖励、高额付费争议和新型批量攻击。

#### 四、第三阶段：反向审查

####### 1. 关键失败场景与修订结论

| 风险 | 反向审查结论 | 本方案控制 | 残余风险 |
|---|---|---|---|
| 形式合法的伪造成绩进入奖励榜 | 授权、额度和顺序只能证明“有权提交”，不能证明真实完成 | 普通离线成绩排除出获奖集合，奖励比赛采用服务端权威竞争局 | 在线自动化仍可能存在 |
| 单账号有界但活动损失失控 | 账号农场可以累加单账号额度 | 增加转换闸门、活动库存、全局预算和资格约束 | 无法完全证明账号对应唯一自然人 |
| 重试、分叉和跨服务部分成功 | 接口幂等不足以保证端到端只发一次 | 以唯一业务结果协调账本、库存、发奖和投影，并支持补偿 | 实现错误需通过故障注入持续验证 |
| 24 小时与真实操作时间不可证明 | 客户端时间不能证明操作发生在有效期内；无法可靠拆分“前24小时操作” | 采用 `play_expire_at` 与 `submit_expire_at` 双期限，宽限期只承担原额度内有限风险，最终超期整批不结算高价值结果 | 宽限期会接受少量可能在第24小时后伪造的声明，需纳入风险预算 |
| 活动截止与离线公平冲突 | 本地完成时间不可验证，立即发奖与 24 小时离线不能同时保证 | 公开宽限期、按持久化接收时间判断、延迟结榜 | 玩家需要接受奖励延迟 |
| 同步后突然回退伤害正常玩家 | 允许超额度展示高价值收益会形成错误承诺 | 提前展示状态和剩余额度，超限转为本地体验 | 提示设计不清仍可能产生投诉 |

####### 2. 主要架构判断

| 判断 | 依据 | 权衡 | 验证方式 |
|---|---|---|---|
| 高价值状态由服务端账本唯一确权 | 客户端完全可控 | 增加对账和预留复杂度 | 经济不变量及状态机测试 |
| 普通离线成绩不进入奖励榜 | 离线过程无法被可靠证明 | 高价值竞争需要短时联网 | 红队伪造分数和赛季演练 |
| P0 离线只能消费预留权益 | 防止多设备复制和回滚 | 未使用预留需要释放机制 | 分叉、过期、退款和故障注入 |
| P1 发放受库存和活动总预算约束 | 单账号上限会被批量账号放大 | 部分奖励需延迟到账 | 无设备关联条件下的账号农场模拟 |
| 高价值活动采用公开宽限期 | 兼顾离线提交与截止一致性 | 延迟结榜和发奖 | 尾部流量压测及结果确定性测试 |
| 风险模型只控制摩擦 | 标签、设备信号可能失效 | 对长尾作弊的检测精度下降 | 关闭模型后的安全降级测试 |
| 超额度提前进入本地体验 | 避免同步后无预警撤销 | 客户端需更清晰提示 | 原型测试、灰度和客服数据 |

####### 3. 验证计划与首轮验收护栏

题面缺少生产基线，因此以下为**建议初始护栏**，必须在影子运行前由产品、财务、风控和 SRE 共同确认，并根据基线调整；它们不是对最终效果的无依据承诺。

| 维度 | 建议首轮护栏/制定公式 |
|---|---|
| P0 账本正确性 | 压测与故障注入中，无来源增加、同一凭据重复兑现、同一预留多分支消费必须为 0；生产发现任一确定性不变量破坏即停止相关能力 |
| P1 库存 | 任何情况下实际发放不得超过总库存、分层库存和预算；重复资格成功发放必须为 0 |
| 排行榜 | 所有可能影响获奖集合的成绩完整重放通过率必须为 100%；未通过或未完成者不得结榜 |
| 双期限语义 | `received_at ≤ play_expire_at` 正常处理；宽限期内只能消费原额度；`received_at > submit_expire_at` 的 P0/P1/P2 高价值结算必须为 0；边界和重试结果必须确定一致 |
| 同步可靠性 | 以当前生产成功率为基线；灰度组相对下降不得超过预登记护栏，且不能出现付费权益永久丢失 |
| 误伤 | 以分层人工样本估算。不可逆处罚精确率要求显著高于可逆暂缓；在取得可靠标签前，模型不得自动永久封禁 |
| 批量风险 | 关闭所有设备关联信号进行压力模拟，总发奖仍不得超过库存与批准预算；奖励集中度超过正常基线高分位时自动暂停对应分层 |
| 人工成本 | 送审率初始上限 0.01% 结算批次并设每日硬上限；超过容量时转为延迟、降级或抽样，不允许积压阻塞全部用户 |
| 性能 | 以容量模型上界加安全余量压测；同步入口以持久化接收成功为 SLA，结算延迟按 P0/P1/P3 分级制定 |
| 单位成本 | 压测后计算每百万 DAU 月成本；超过批准预算时优先减少 P3 原始数据、重放范围和模型特征，不削弱 P0/P1 不变量 |

########## 3.1 基线建立

至少覆盖完整活动周期、版本发布和典型网络波动，收集：

- 离线时长及弱网分布；
- 同步载荷、重试率和尾部流量；
- 资产来源、消费及完整转换图；
- 历史作弊损失和奖励集中度；
- 支付补单、退款及客服争议；
- 存储、计算和人工审核成本。

不能只把历史封禁账号作为作弊样本，应通过红队、分层人工抽样和申诉结果补充标签。

########## 3.2 架构不变量验证

- 对账本、预留、释放、退款、库存和发奖状态机进行属性测试。
- 注入重复、乱序、崩溃、超时、主从切换和跨服务部分成功。
- 验证同一支付、预留、资格和业务结果不能重复兑现。
- 验证投影或风险服务故障不改变权威资产事实。
- 验证合法购买在各种故障后仍可恢复。

########## 3.3 红队与批量攻击

覆盖：

- 伪造最终分数和形式合法的操作序列；
- 回滚、重放、旧版本和修改本地时间；
- 多设备并行分叉及选择性提交；
- 广告回执重放；
- 大量账号分别取得合法额度；
- P2/P3 通过转换链路攻击 P1；
- 活动结束前后的集中提交；
- 客户端完整性和设备关联能力完全失效。

########## 3.4 弱网和用户体验验证

- 模拟丢包、乱序、重复、长延迟和客户端崩溃。
- 分别观察普通用户和弱网用户。
- 测试“已确认、可结算暂定、本地体验”三种状态的理解程度。
- 统计同步失败、错误限制、申诉成功、留存变化和客服工单。
- 所有体验护栏在实验前登记，不能在看到结果后调整。

########## 3.5 影子运行和灰度

1. 新策略先影子运行，不改变用户结果。
2. 先上线 P3 声明式同步和可观测性。
3. 一致性验证通过后再上线 P0 预留消费。
4. 库存、资格和申诉闭环成熟后上线 P1。
5. 奖励排行榜在服务端权威竞争路径完成红队验证后启用。
6. 每阶段均保留按版本、活动和转换路径回滚及熔断能力。

####### 4. 验证失败后的退出路径

| 风险 | 调整路径 | 最终退出路径 |
|---|---|---|
| 奖励成绩无法可靠验证 | 缩小竞赛玩法范围，加强服务端状态控制 | 奖励比赛改为联网玩法或取消高价值奖励 |
| 批量账号风险超过预算 | 收紧资格、关闭高风险转换、降低活动总暴露 | 稀缺奖励不得由离线进度取得 |
| 账本一致性未通过 | 只上线 P3，同步保留候选结果但不发放高价值权益 | P0/P1 操作暂时要求联网 |
| 宽限期导致运营不可接受 | 优化授权窗口和延迟发奖流程 | 高价值活动要求截止前联网提交 |
| 误伤或人工成本超标 | 降低模型处置强度，扩大可逆处置 | 停止模型驱动限制，仅保留确定性额度和闸门 |

任何退出都优先关闭兑换、发奖和竞争入口，不关闭普通离线闯关，也不删除待恢复的合法购买权益。

####### 5. 明确残余风险

本方案仍不保证：

- 识别每一个修改客户端或使用自动化的玩家；
- 证明账号对应唯一自然人；
- 完全消除联网奖励比赛中的自动化；
- 精确恢复所有 P3 普通资产；
- 在不增加身份验证和隐私成本的前提下彻底解决账号农场。

这些风险只有在不突破 P0/P1 安全不变量、活动风险预算和体验护栏时才可接受。

#### 五、进入详细设计条件

以下条件全部满足后，方可进入接口、字段、状态机和技术选型层面的详细设计。

####### 1. 产品语义已确认

- 24 小时被明确为 `play_expire_at` 候选游玩期限，而非操作时间证明；`submit_expire_at` 宽限长度、风险预算、迟交批次、断续联网、跨设备和最终超期恢复行为均已签字。
- “已确认、可结算暂定、本地体验”的用户承诺已明确。
- 活动宽限、结榜、发奖和迟到补偿规则已确认。
- 奖励榜与非奖励榜的边界已确认。
- 超额度提示和后续收益规则已通过用户测试。

####### 2. 经济边界已证明

- 已完成全部资产来源、消费和转换图。
- 每条通向 P0/P1 的路径都有服务端闸门。
- 单账号、单窗口、转换路径和活动全局预算均已定义。
- 财务、经济和风控已批准损失预算。
- 在不使用设备指纹和账号关联信号时，P0/P1 仍受确定性约束。

####### 3. 竞争边界已决定

- 所有排行榜是否发奖已经分类。
- 奖励排行榜的服务端权威竞争路径已经确定。
- 客户端自报最终分数不能直接进入获奖集合。
- 无法验证的离线成绩已明确进入个人或非奖励榜。

####### 4. 一致性模型已评审

- `OfflineGrant`、`OperationClaim`、`SyncClaim`、`Reservation`、`RewardQualification`、`LedgerEntry`、`Settlement`、`CompetitionSession` 的责任和唯一约束明确。
- 授权签名/MAC、服务端权威查询、密钥轮换、吊销、会话绑定、跨账号重放和旧版本兼容策略已完成安全评审。
- 权威账本、预留、消费、释放、退款、库存和发奖责任边界明确。
- 授权、预留、声明和奖励资格状态机已经评审。
- 重试、分叉、过期、兄弟分支后果以及跨服务部分成功的补偿原则明确。
- 合法购买恢复路径已通过各支付平台验证。
- P0/P1 重复发放和合法购买永久丢失被定义为不可接受的不变量。
- 运营补发和人工调整具有统一、可审计的账本入口。

####### 5. 数据与阈值已建立

- 弱网、离线时长、每日同步次数、每批声明数、批次载荷、同步峰值和重试放大基线可用。
- 日账本分录量、热冷数据保留、排行榜重放量、审核比例和每百万 DAU 成本模型已完成压测校准。
- 多地域归属路由、账本一致性、分区迁移、活动库存协调、队列背压、RPO/RTO 和各资产结算 SLO 已通过压测与故障演练。
- 历史攻击、红队样本、申诉和分层人工标签可用。
- 财务损失、用户体验、容量及人工成本门槛已预登记。
- 宽限期和发奖时效基于真实尾部流量制定。
- 策略评估具备足够统计功效，且不在实验后修改通过标准。

####### 6. 运营与隐私闭环可执行

- 具备暂停兑换、暂停发奖、降低额度和按版本熔断能力。
- 申诉、恢复、补偿和审计责任人明确。
- 客服容量与预计工单量匹配。
- 隐私影响评估通过，数据目的、权限和保留期限确定。
- 删除设备关联数据后，核心安全不变量仍能成立。

####### 7. 最终准入判断

只有当以下三项得到验证，方案才可进入详细设计和分级上线：

1. **客户端只能声明，高价值结果由服务端最终确权；**
2. **客户端完全失守且批量账号出现时，P0/P1 总风险仍受确定性约束；**
3. **弱网体验、隐私、基础设施和人工运营成本均未突破预登记护栏。**

满足这些条件后，系统可以在保留最长 24 小时普通离线闯关的同时，将不可逆、高价值和全局竞争结果留在服务端可信边界内，从而把作弊风险控制在团队能够持续承担的范围内。
