# 调研发现

## 仓库/范围
- 目标插件位于 `work/scripts/pi/pi-notification`，不是 `work/scripts` 根。
- `/notify` 唯一入口：TUI 打开 `NotifySettingsComponent`，非 TUI 打印状态和配置摘要。
- 工作区已有用户改动：`plans/archive/plugin-development-notes/README.md` 被删除；保留该状态。

## 当前交互（初步）
- `src/ui.ts` 目前是多层设置浏览器，含分类、事件规则、候选表、搜索、字段帮助、预览、邮件凭据设置、状态诊断、还原、快捷键等。
- `src/commands.ts` 提供强大的通用设置 host；值分为出厂默认、用户默认、当前会话；Enter 应用当前会话，Ctrl+S 持久化单字段。
- README 指南已经很长，涵盖配置 schema、三层值、各快捷键和安全语义。配置表达本身对非开发者较重。
- 关键安全语义：自检已提交不等于送达；QQ 凭据使用系统凭据管理器；默认只发 terminal；强制静默覆盖设置；敏感渠道 options 不显示。

## 当前 JTBD 假设（尚无客户研究）
- 「离开电脑/终端时，知道长任务何时完成或失败」是目标任务，不是“配置通知 schema”。
- 关键决策可能被压缩为：要不要通知、哪类结果、送到哪里、是否现在验证。
- 最大风险：高级字段一股脑呈现，使用户不知道先配什么；设置后没有把“如何判断可用”放在主路上。

## 进一步盘点
- 设置表超过 50 项，主屏目前列出总开关、全局最低等级、5 个分类；分类有规则、内容、安静时间、渠道、投递/频率高级项。
- 规则页是二级列表再进单规则详情（开关、级别、渠道等），Space 当前只处理字段，对规则行无效。
- 渠道页中 Email 还需再打开一层配置页：发件/收件地址、凭据、QQ 官网链接、独立邮箱测试；主屏没有「测试通知」动作。
- 邮件状态和渠道标识部分使用 SMTP、QQ SMTP、Windows 凭据管理器、email/hook 等配置概念；对只想收到提醒的用户不直观。
- 邮箱密钥的安全存储仅 Windows 可用（`src/mail/credentials.ts` 在其他系统返回不可用），环境变量只作为旧配置回退；UI 文案需保留平台诚实性，不可泛称跨平台安全存储。
- 高级设置动作混在投递/频率字段同一页；简单用户不需要先看到全量参数，但测试/诊断是核心验证路径。
- `test/settings-ui.mjs` 对现有页面结构有很多确定性断言；需更新主路径契约，并确保保留凭据/恢复/安全/窄屏行为。

## 方案收敛
主屏改成直达日常任务的轻量菜单：总开关、提醒场景、提醒送达方式、直接测试、更多设置。最低等级从主屏移至更多设置；高级菜单承载内容、免打扰、投递选项及状态/搜索/重读。规则行支持 Space 即时开关，降低进入层级；英文渠道 id 显示友好中文名。邮箱当前“未配置”摘要和设置说明改成用户任务语言，同时明确授权码需 QQ 邮箱授权码而非登录密码，且安全存储仅 Windows 可用。测试需更新首页结构、快速切换、Email 状态文案和全屏扫描，保留原有安全回归。

## 实施与验收
- 主屏精简到常见目标；最低提醒级别、内容、免打扰、投递/频率等放入更多设置，状态/重读/搜索也归入该入口。
- 测试通知直接可达；提醒场景可用 Space 启停；父页面返回后重建以更新摘要。
- 使用友好渠道名及邮箱配置状态；邮箱测试提示下一步且不夸大送达保证。凭据仅在 Windows 提供 UI 安全保存，不改旧环境变量兼容机制。
- README 路径说明已更新；全量测试通过，`git diff --check` 通过。产品假设仍待真实用户研究验证。
