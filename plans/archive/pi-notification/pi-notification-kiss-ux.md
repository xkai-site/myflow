# pi-notification：JTBD / KISS 配置体验开发方案

## Context

用户同时使用本机与邮箱提醒。已确认：修改默认只影响本对话，Ctrl+S 将当前项已生效的值保存为长期默认；长期配置集中在一个 JSON，支持用户或 Agent 编辑；TUI 提供渐进式逐项配置。不使用 planning-with-files 配套文件。

核心 Job：**当我让 Pi 执行任务并转去做其他事情时，我希望在执行结束或需要我处理时得到提醒，从而不必反复回来查看。**

目标收益：装好能用、提醒可理解、接收方式容易配置、知道为什么没收到。功能上区分完成/失败/等待输入并辨认会话；情绪上希望放心离开且避免频繁打断；社交需求没有证据，不为此添加新设置。替代方案还包括盯着终端、定期切回和不管它。

不新增安静/标准/专家等运行模式，不削减可靠性、安全与专业配置能力。代码证据不是用户访谈。用户再次引用的初版建议中，“普通修改自动长期保存”不采用，遵循其明确确认的本对话优先及 Ctrl+S 语义。

## 已发现的实现约束

- 设置描述表提供 47 个字段，其中规则字段 21 个；首页已有渐进展示，主要问题是规则开关/等级/渠道及 provider 开关的交叉关系。
- 当前 `RuleConfig.channels` 是必填数组，默认六条规则各自使用 terminal；没有真正的统一渠道继承。
- 邮箱凭据就绪、provider 开启与规则路由到邮箱是独立条件；界面“已准备好”不足以表达实际可用性。
- `writeUserDefault()` 已支持多字段 patch 的一次校验和原子写入；可复用，避免逐字段写盘导致部分成功。
- `mergePatch()` 的数组语义是整体替换。provider patch 必须以原始用户配置为基准，仅更新目标项，不能把有效配置整体写回。
- `applyOverlay()` 与会话 entry 已实现会话覆盖；new/fork 不继承，reload/resume 保留。保持这些契约。
- `adoptConfig()` 显式逐字段复制配置；新增字段必须接入此处，否则重读与会话更改不会生效。
- 测试通知目前使用 runCompleted 的渠道和 info 等级，service 仍检查 minLevel；submit 返回 void，不能可靠反馈“是否入队”。
- 本次开始检查时 git 工作区干净。计划阶段仅修改本 Markdown，不修改实现、不安装依赖、不发送真实通知。

## Approach

### 已确认方向

1. 保留 `/notify` 单一入口，首页展示启用提醒、提醒时机、接收方式、测试、更多。
2. Enter/Space 即时应用于本对话；Ctrl+S 仅保存当前逻辑配置项，不保存所有会话修改或悬停候选。
3. 本机与邮箱可多选；统一接收方式应有真实继承语义，不能仅用“跟随”文案掩盖独立数组。
4. 保留自定义逐规则路由；已有配置不静默重写。启用远程渠道须明确用户意图，不能因配置地址/保存凭据而自动外发。
5. 同一个 JSON、同一套校验支撑 UI 和 Agent 编辑；Ctrl+R 重读后保持会话覆盖并明确标识，支持沿用长期默认。
6. 测试针对接收渠道，绕过业务等级/免打扰/频率筛选，不绕过强制静默、总开关或渠道禁用。区分未发送、排队/发送中、渠道接受与失败；渠道接受不等于用户看到。
7. 消息 API 不纳入人类提醒的统一接收方式，不改变其独立开关、协议和隐私边界。

### 已确认的产品边界

- 逐规则渠道、等级保留在“更多 → 专业设置”；逐规则不同渠道很少使用，不放在普通路径。
- 合并/冷却/超时/重试/并发/队列/熔断/收尾预算等参数退出 TUI，仅保留 JSON；工具失败策略/阈值及等待输入种类也仅留 JSON。
- 普通路径保留完成、失败、等待输入，更多保留内容与隐私、免打扰、诊断。
- P0：减少规则/渠道交叉决策、邮箱配置后无需逐规则选渠道、明确单项临时/长期作用范围、修复测试被 minLevel 拦截却提示已提交。P1：准确区分邮箱配置就绪、被路由使用、投递是否完成。

### 已核实的复用与兼容注意点

- `rules.ts` 四类请求构造都直接读取 `rule.channels`；在规则层统一解析有效渠道，service 继续只接收明确的渠道数组，不在投递层解释配置继承。
- provider 校验保留自定义数组替换语义，仅有 email 的稀疏数组会补 terminal；不能普遍改成合并数组，否则破坏旧配置。
- `registry.create()` 对未注册、不可用渠道降级为带原因的 noop；测试报告必须将 skipped 单列，不得当作成功。
- `service.deliver()` 已产生逐渠道 `DeliveryResult` 并更新计数；复用投递管线做关联测试结果，而不是另写直连 SMTP/终端路径，也不能用前后总计数差值猜测测试结果。
- 邮箱按收件人记录 SMTP 接受并可重试，错误只公开限长的允许代码；UI 沿用脱敏结果，不额外暴露服务器原文或凭据。
- runtime 在普通事件中调用同步 `service.submit()`；保留同步非阻塞行为，异步观察只给显式手动测试使用。

### 1. 渐进式 TUI 与普通提醒项

```text
通知                         修改仅本对话生效

启用提醒                     开启
什么时候提醒                 完成、失败
在哪里接收                   本机、邮箱
发送测试提醒
更多                         内容与隐私、免打扰、专业设置、诊断

Enter 配置 · Space 切换 · Ctrl+S 保存当前项为长期默认
```

- “什么时候提醒”只展示三个逻辑项：执行完成（runCompleted）、执行失败（runFailed + compactFailed）、需要我回复（waitingForUser）。完成表示 Pi 已停止自动执行，不保证业务目标成功；失败明确涵盖运行或上下文压缩失败，不包括每次可恢复工具失败。
- 完成/失败沿用当前默认开启，等待输入仍默认关闭，不借 UX 改造改变通知偏好。工具失败仍默认汇总，取消仍默认不提醒。
- 失败的两个底层开关不一致时显示“部分开启/自定义”，不自动归一。用户明确选择开启/关闭才同时修改二者；Ctrl+S 在未统一前保存当前两项各自状态，不把混合状态强制转为 boolean。
- “更多 → 内容与隐私”保留内容字段及预览，回复摘录默认关闭；“免打扰”保留时间及等级例外，关闭时折叠参数。
- “更多 → 专业设置”保留 minLevel、六条规则各自开关/等级/路由及 provider 可用开关、邮箱主题前缀。这是低频编辑入口，不是另一套运行模式。
- 工具失败策略/阈值、等待输入类型、投递与频率参数退出 TUI **设置表及搜索结果**，只在 JSON 编辑和只读诊断中出现；不让搜索绕过简化边界。
- 三层来源详情仍可查看；首页只显示作用范围与必要警告，不反复输出所有层级。保留 ?、a 沿用长期默认、d 确认恢复内置默认、Ctrl+R 重读、Ctrl+O 诊断。可复用启用提醒开关暂停本对话，无需新增重复暂停功能。

### 2. JSON 与真实的统一渠道继承

新增顶层 `channels: string[]`，默认 `["terminal"]`；规则 `channels` 扩展为 `"inherit" | string[]`，默认 inherit。仍为 version 1 的向后兼容扩展：新版本读取旧配置，旧插件不支持新值，README 提醒使用新配置前升级插件。

```json
{
  "version": 1,
  "channels": ["terminal", "email"],
  "providers": [{ "id": "email", "type": "email", "enabled": true,
    "options": { "from": "sender@qq.com", "to": ["reader@example.com"] } }],
  "rules": {
    "runCompleted": { "channels": "inherit" },
    "runFailed": { "channels": "inherit" }
  }
}
```

- 单个纯函数解析 `rule.channels === "inherit" ? config.channels : rule.channels`；四类规则构造均复用，service、Webhook 和运行事件继续接收明确渠道数组。
- 空顶层数组表示统一路由不投递；显式规则 `[]` 表示该规则不投递；数组去重保序。未知/已删除 provider id 保留以便发现并修复，诊断提示不可用，不静默改成其他渠道。
- 旧文件显式规则数组、level、provider 定义原样保留；旧会话数组 patch 仍有效。缺失字段从 base 合并，不误清除已有 override。未配置路由的新旧用户仍默认仅 terminal；无需启动迁移或写盘。
- 已有自定义路由即使恰好等于统一渠道也仍显示“自定义”，不根据相等性假定继承。专业界面支持明确“跟随统一设置”或自定义多选。
- 接收方式以顶层 channels 为主；明确选中某 provider 时同时开启该 provider。远程渠道提示其将用于已开启且跟随统一设置的提醒；填写地址/保存凭据不自动加入渠道。
- 取消统一接收选择仅移除顶层路由，不禁用仍被自定义规则使用的 provider。首页及接收页提示仍存在自定义例外；彻底停用某 provider 在专业设置操作。避免双重开关成为普通操作必选步骤。
- 修改统一渠道不会清除规则 override；需要归一旧路由时提供“让所有提醒跟随统一接收方式”的明确确认，列出受影响规则，默认取消。确认仅将六条规则 channels 置为 inherit，不更改开关/等级。此操作默认仅本对话；结果页 Ctrl+S 以一个逻辑项保存六条渠道，不保存其他修改。
- 安全降级仍明确仅本机失败提醒，禁止继承用户的远程渠道；API 降级行为不变。`adoptConfig()` 接入顶层 channels，describeConfig/状态/预览均用有效渠道和来源准确展示。

### 3. 逻辑配置项、单项保存与还原

- 在现有 SettingItem/SettingPatch 上增加最小的复合项描述：拥有的配置路径/provider 字段、有效值快照、格式化和应用操作。失败开关、接收方式、统一路由动作均复用同一套机制，不在 commands/ui 到处硬编码路径。
- Enter/Space 先构建完整 overlay 候选并调用已有 applyOverlay/mergeConfig 预校验，通过后只 setOverlay 一次；失败不部分应用、不把错误值写进 session entry。敏感 headers/URL/授权码不进入复合项或会话数据。
- Ctrl+S 从 **当前已生效逻辑项快照** 构建稀疏 patch；单字段只保存该字段，复合项只保存其拥有的字段。失败项保存两个开关；接收方式保存顶层完整渠道数组及选中 provider 当前已生效的 enabled 值（一般为明确选择时开启的 true；后续专业页禁用不能被保存动作偷偷重新开启），不保存地址、授权码、规则路由或其他会话设置；统一路由动作仅保存六个 channels。
- provider 数组必须在一次写事务内基于最新 raw JSON 构建，保留其他 provider、options、安全引用和未知字段；不从有效配置整表拷回。抽取当前读原始文件→构建稀疏数据→全量校验→原子写入的共用内部函数，writeUserDefault/deleteUserDefault 复用；复合删除也走同一事务，不循环调用单项写入。
- 保存成功后重读；明确“已保存当前项为长期默认，其他本对话修改未保存”。保存失败不变更磁盘或会话覆盖。保存保留本项会话覆盖，与现有语义一致；选择 a 才清除该项拥有的覆盖，沿用长期默认。
- 复合项操作应记录其确切字段范围：失败项固定两个 enabled，统一路由项固定六个 channels；接收项为顶层 channels 及选中/该项此前明确开启的 provider enabled。必要的字段范围元数据仅含路径/id，作为会话 entry 可选字段保存，恢复时只允许该逻辑项的白名单字段，拒绝任意路径及 API/安全字段；旧 entry 缺少时只认已有可证明的覆盖，不凭猜测删除其他项。专业页后续显式修改同一 provider 开关时转移该字段的操作归属，避免接收项还原误清除它。
- d 在确认页列明上述范围，原子删除当前项拥有的长期字段并清除同范围会话覆盖；不删除 provider 定义/options，不顺带恢复等级或规则开关。规则自定义渠道恢复为 inherit。复合项来源混合时显示“部分本对话覆盖/部分长期默认”，不伪装成单一来源。
- 会话 entry 沿用现有格式与 sessionId 约束；保留 reload/resume 覆盖、new/fork 不继承、空快照清除语义。Agent 修改 JSON 后通过 Ctrl+R 生效，被本对话覆盖的字段继续明确标识。

### 4. 邮箱是一个渐进配置任务

- 在接收方式页面，选邮箱但参数不齐时进入邮箱页；步骤依次展示发件地址、收件地址、授权码状态、明确启用并加入统一接收方式、发送邮箱测试。参数逐项 Enter 生效、Ctrl+S 保存；主题前缀沿用 `[Pi]`，放专业页。
- 本机和邮箱支持同时选择。不强制一次性表单保存、不新增长期 draft 文件；中途 Esc 保留已明确提交的本对话参数，未提交的输入取消。
- 为遵守“不向禁用渠道发送”，采用 **先明确确认启用，再测试** 的顺序。测试按钮不能替用户隐式开启；测试失败保留用户明确选择，显示可修复原因，不自动关闭或改路由。
- 地址和授权码填写完不自动启用、不自动测试，所有外发由确认或测试动作产生。授权码继续仅在 Windows 凭据管理器保存，跨系统环境变量回退不变；此安全操作即时保存的范围须明确，不误标为本对话。
- 展示“未配置/缺地址/缺授权码/已选择但不可用/配置就绪未测试/已提交给 SMTP”等真实状态，同时提示使用统一路由的规则数量及自定义例外；没有规则引用时显示“尚无提醒使用”，不显示笼统的“已准备好”。测试结果不持久化为长期健康保证。
- 已经有显式旧路由的用户，启用邮箱后若不会用于任何规则，直接展示归一入口；未经确认不改路由。统一邮箱选择仅影响继承统一设置的已开启提醒；自定义规则按自己的渠道投递，文字不承诺所有例外也会收到。

### 5. 可解释的渠道测试与投递反馈

- 首页/ Ctrl+T 针对当前统一接收渠道发送固定无敏感内容测试；专业规则详情可测试其有效路由；邮箱页只测 email。既有规则关闭不阻止显式渠道测试，不再依赖 runCompleted 的数组或等级。
- service.submit 维持同步非阻塞，返回结构化受理结果（accepted/rejected + 原因）；仅增加显式 manual-test 标记时绕过 minLevel/免打扰/合并/冷却，不扩大现有 bypassFilters 的普通通知语义，不用伪造 error 级别绕过门槛。
- 使用内存请求关联（独立 testId/dedupeKey）及可取消的进度订阅，复用 existing deliver() 的逐渠道 DeliveryResult；不加入真实 Webhook 载荷字段，不从全局计数推测结果，不引入事件总线或另写发送通道。
- 立即报告未发送/已排队，实际取出时报告发送中，逐渠道报告 accepted/failed/skipped。分渠道显示部分成功；终端写入/系统接口返回仅表示已提交给终端或系统，SMTP/HTTP 返回仅表示服务接受，不承诺可见/到箱。
- 有界队列拒收、挤掉旧测试、去重、disposed、未知渠道、禁用渠道、noop 降级、异常及 discardPending 都须产生明确终态或未受理原因。pending 内存不超过队列/并发边界，不无限累计历史测试。
- 总开关及 --no-notify / PI_NOTIFY_DISABLE 在预检和实际发送前检查；测试也不绕过 provider 禁用。强制静默期间不能开启外发。正常通知的重试/超时/队列策略不改变，测试与普通流量共享现有投递机制。
- SettingsHost 测试方法接入异步进度；组件仍可导航，必要时限制重复测试；每轮结果按 testId 关联，不让较旧结果覆盖新测试。仅活跃页面更新渲染/焦点不动；关闭 custom UI 时取消订阅，已明确发起的投递可继续并计入诊断，禁止晚到回调重开页面或访问旧 ctx。
- 诊断首屏先给当前阻断原因和下一步，再展示统计/高级参数；API 状态单独展示。其余正常通知的监控/排队算法重构不在本次范围。
